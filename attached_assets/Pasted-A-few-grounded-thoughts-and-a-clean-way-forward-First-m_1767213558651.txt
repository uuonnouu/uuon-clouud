First — mindset (important)
	•	It’s okay that features aren’t working yet.
Almost every serious platform launches in a “partially inert” state.
	•	Shipping early gives you:
	•	Real URLs
	•	Real constraints
	•	Real debugging signals
	•	You now have something you can stabilize instead of imagine.

⸻

Immediate sanity checks (fast wins)

Do these in order—no refactors yet:
	1.	Confirm the domain
	•	Double-check whether it’s .com vs .con
	•	Make sure DNS → hosting → build output are aligned
	2.	Open DevTools (mobile + desktop)
	•	Console errors (red = priority)
	•	Network tab → failed fetches / blocked SDKs
	•	Look for:
	•	CORS issues
	•	Missing env vars
	•	404s on assets
	3.	Identify “silent failures”
	•	Features that don’t error but don’t respond
	•	Usually:
	•	Event listeners not bound
	•	SDK init not firing
	•	State not hydrating

⸻

Classify broken features (this matters)

Don’t fix randomly—label them:

🟢 Cosmetic
	•	UI loads, visuals off, animations missing
→ Lowest priority

🟡 Interactive
	•	Buttons, sliders, canvases not responding
→ Medium priority (often event/state issues)

🔴 Structural
	•	Engines not initializing
	•	Visualizers not rendering
	•	SDKs/APIs returning nothing
→ Fix first

If you want, you can paste a feature list and I’ll help you classify them in 2–3 minutes.

Since you’re moving from APIs → SDKs (your earlier goal)

Common launch breakpoints I’ve seen that match exactly what you’re describing:
	•	SDK loaded but:
	•	Not awaited
	•	Not attached to window
	•	Not initialized before render
	•	Frontend trying to call:
	•	Old API endpoints that no longer exist
	•	Build-time vs runtime mismatch
	•	Works locally, fails live

This is normal, not failure.
